# SQLite in production

MatMix uses schema version `8` (`PRAGMA user_version`). Version 7 adds the transactional `order_email_outbox` for new-order email events; version 8 adds Web Push subscriptions and the transactional push outbox. Production startup refuses any other version, and migrations are deliberately separate from startup. Migration 7 → 8 creates the empty push tables and does not enqueue historical orders.

Before deployment, stop the application and run `npm run database:migrate -- --dry-run`. Review the orphan report, then run `npm run database:migrate -- --apply --confirm MIGRATE_MATMIX_DATABASE`. Apply refuses to run while the runtime lock exists and creates a consistent `VACUUM INTO` database backup before `BEGIN IMMEDIATE`. A failed migration rolls back; keep the application stopped, inspect the error and restore the generated backup if required.

Every writable business connection enables `foreign_keys=ON`, `journal_mode=WAL`, `synchronous=NORMAL` and a 5000 ms busy timeout. Read-only backup verification does not change journal mode. WAL improves reader/writer concurrency but does not eliminate writer contention; exhausted waits are returned by the API as controlled `503 DATABASE_BUSY`, while constraints become `409 DATABASE_CONFLICT`.

Run `npm run database:health -- --json` after migration and before startup. It checks the schema version, integrity, foreign keys, required indexes, orphan and duplicate counts, entity totals, and image-reference totals without printing personal data. Backup, verification and restore procedures remain those in `docs/backup-restore.md`; restore must be performed with MatMix stopped, followed by the health check.

Version 1 adds `orders.client_id -> clients.id ON DELETE SET NULL` so client removal cannot erase order history, and `order_events.order_id -> orders.id ON DELETE CASCADE` because events are technical children. Version 7 adds `order_email_outbox.order_id -> orders.id ON DELETE CASCADE`, a unique deterministic `event_key`, and the worker lookup index `(status, next_attempt_at, id)`. Version 8 adds `web_push_subscriptions` and `web_push_outbox`, ownership FKs, endpoint/order-subscription uniqueness, and worker retry indexes. `catalog_structure.parent_id` retains its restrictive default. Product names and `items_json` are historical snapshots and intentionally have no foreign keys.

## One-shot order email worker

`npm run email:orders:process` performs one bounded pass over at most 20 eligible outbox events and exits. It requires the `MATMIX_ORDER_EMAIL_*` variables shown in `deploy/matmix.env.example`; the normal web server neither loads nor validates them. Port 587 uses explicit STARTTLS (`secure: false`, `requireTLS: true`) with certificate verification enabled. Connection, greeting and socket timeouts are 10, 10 and 30 seconds. No timer, cron or systemd unit is installed by this stage.

Each event is claimed in a short `BEGIN IMMEDIATE` transaction. SMTP runs only after that transaction commits, and final status is written in a second short transaction conditional on the exact claim timestamp. A `processing` row older than 15 minutes is eligible for recovery. Failed sends use at most eight persisted attempts with deterministic exponential delays starting at one minute and capped at six hours. Error text is sanitized and bounded before it is stored; credentials, transport configuration and message bodies must not be logged.

Delivery is intentionally **at least once**, not exactly once. `attempt_count` records worker attempts whose normal `sendMail` success or error finalization was persisted in SQLite. If SMTP accepts a message (or was invoked) and the process exits before finalization, stale recovery can send a duplicate while the interrupted physical SMTP attempt is absent from `attempt_count`. Consequently, eight is the persisted-failure limit, not an absolute upper bound on physical SMTP calls during process crashes. The deterministic `event_key` prevents duplicate outbox events for an order but cannot provide SMTP idempotency. File-request emails list attachment names only and never attach binaries or expose storage paths.

Web Push follows the same **at-least-once** boundary: a crash after provider delivery but before `status='sent'` can make stale recovery deliver again. The payload carries a server-derived `eventId` (`order-<numericOrderId>`), and the Service Worker uses the corresponding deterministic notification tag to suppress an existing duplicate on a best-effort basis. This UI deduplication is not an exactly-once guarantee and does not replace stale recovery or retries.
